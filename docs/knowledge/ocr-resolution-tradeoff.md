# OCR 分辨率 ↔ 耗时 ↔ 识别召回（2026-09-17）

## 结论

**不要把分辨率降下来。** 半分辨率的 OCR 大约只省 0.15–0.2 s，却要少认 **~20–25 % 的字**；
而 OCR 在「按一次眼镜拍照键 → 眼镜里听到声音」这条 2.3 s 的链路里只占 ~0.3 s（约 14 %）。
真正的瓶颈已经在眼镜端拍照的 ~1.3 s（固件侧），不在识别。

## 实测

方法：`tools/ocr-resolution-sweep.py`（离线），复用 `tools/ocr-audit66-fixtures.py` 的
同一份 PP-OCRv6 det/rec ONNX 模型与前后处理，只扫 `det_limit_side_len` / `limit_type`；
数据源是 `违规案例/` 里前 20 张真实案例图（手机拍的真实场景，不是合成图）。

| 检测输入上限 | 耗时中位 | 耗时均值 | 行数中位 | 相对 960 的字符召回 |
|---|---|---|---|---|
| 1280 / min（fixture 脚本当前设置） | 1680 ms | 3132 ms | 11.0 | 0.960 |
| **960 / max（Android `PaddleOcrEngine` 当前设置）** | **611 ms** | 700 ms | 9.5 | **1.000** |
| 768 / max | 684 ms | 992 ms | 8.5 | 0.886 |
| 640 / max | 668 ms | 899 ms | 8.0 | 0.862 |
| 480 / max | 287 ms | 553 ms | 7.5 | 0.769 |
| 360 / max | 325 ms | 483 ms | 6.5 | 0.715 |

> - 绝对耗时是 **PC CPU** 的；手机端同为 CPU 推理，**趋势**可迁移（手机端实测
>   `CRC → 语音开始` 共 0.32 s，其中含解码/OCR/规则匹配/TTS 预热）。
> - 「字符召回」= 候选文本按字符多重集合覆盖 960/max 文本的比例，1.000 = 一个字都没少。
>   这是**相对**指标（不是绝对准确率），但足以说明「少认了多少字」。
> - 1280/min 反而比 960/max 召回更低（0.960）：对偏小的图它会放大，放大后的 DB 后处理
>   会把相邻文本块合并/切碎 —— 也说明「分辨率越高越好」并不成立，960/max 是当前甜点。

复现：

```bash
python tools/ocr-resolution-sweep.py --images 20
python tools/ocr-resolution-sweep.py --images 20 --settings 1280:min,960:max,640:max,360:max
```

报告落在 `build/reports/ocr_resolution_sweep_<时间戳>.md`。

## 与端到端耗时的关系（V2.6.2，2026-09-17 实测）

| 阶段 | 耗时 | 占比 |
|---|---|---|
| 按键 → 首块（眼镜端拍照） | ~1.34 s | 58 % |
| 传图（51 KB / 213 块 / 0 补洞） | 0.59 s | 26 % |
| 收齐 → CRC 确认 | 0.04 s | 2 % |
| CRC → 语音开始（解码+OCR+规则+播报） | 0.32 s | 14 % |
| **合计** | **≈ 2.3 s** | |

若要再压缩，优先级应是：① 眼镜端拍照（固件）→ ② 传图（已从 7.5 s 降到 0.6 s）
→ ③ OCR（现在这 0.32 s 里还要算上解码与播报预热，能压的空间最小）。
