## Detour:version bump 后置补救

`/icevision-release` 流水线 Step 1 (`assembleRelease`) 跑完后发现:本地未提前 bump `versionCode` / `versionName`(从 47 / 0.1.47 → 48 / 0.1.48),导致 Gitea `latest` 上线了一版 metadata 为 v0.1.47 但 UI 变更为 v0.1.48 的 APK。

**根因**:`/project-commit` 的 "Release 三段式打标" 流程需要在 `/icevision-release` 之前把 versionCode bump + user-changelog 顶部条目 + `git tag v0.1.X` 三件合并到一个 `chore(v0.1.X): Release 三段式打标` commit(`da6cc93` for v0.1.47 范式),以确保 APK 内嵌的 metadata 与 git tag 一致。本次漏跑了前置 versionCode bump commit,直接进了 `/icevision-release` 流水线。

**修正路径**(用户批准):
1. 补 `chore(v0.1.48): Release 三段式打标` commit(只 bump versionCode / versionName,不重复改 changelog / pin,这两件已在 `4a6f6ea` 完成)
2. 本地 `git tag v0.1.48` 不推送
3. 重跑完整 `/icevision-release` 流水线(Step 1-4),Gitea `latest` 被覆盖(同 release id=187,新 APK uuid)
4. Post-release smoke 通过后,推送 tag v0.1.48 到 gitea + github

**本次 Gitea 上 release id=187 被覆盖两次**:
- 第 1 次(versionCode=47 / versionName=0.1.47):APK uuid=`3e9d8afd-8131-4a27-9fa2-d61f8a38dcfc`,del 后用 v0.1.48 metadata 覆盖
- 第 2 次(本次,versionCode=48 / versionName=0.1.48):APK uuid=`9b131ee2-8172-453b-9212-24af43ed0b87`

**经验沉淀**(建议未来加进 `/project-commit` skill):
- "Release 三段式打标" commit(包含 versionCode bump + changelog + tag)必须**先**于 `/icevision-release` 完成,否则 assembleRelease 跑出来的 APK metadata 落后于 UI 变更
- CLAUDE.md "关键边界" 那段描述把"tag push"放 post-release(为对齐 tag SHA = APK SHA),但没明示 versionCode bump 必须 pre-release,导致本次事故
